# Compiler-Authority Protocol

Applies whenever the AL compiler / analyzers (`al compile` / `al_build` / `al_compile` / `al_getdiagnostics`) report a diagnostic — an `ALxxxx`/analyzer code (CodeCop `AAxxxx`, AppSourceCop/PerTenantExtensionCop, UICop, or the ALCops suite — ApplicationCop, DocumentationCop, FormattingCop, LinterCop, PlatformCop) with a file:line — for code written or edited this session. **A diagnostic is any severity, not just `error`.** A build that "succeeds" with new warnings on code you touched is not done.

## 0. All ALCops, every time — warnings are not optional

**The Full Analyzer Set** (this is the one, non-negotiable list — never a subset of it, never "whichever the tool defaults to"):
`${CodeCop}`, `${PerTenantExtensionCop}` (PTE) or `${AppSourceCop}` (AppSource/Global — per the project's `app.json` target), `${UICop}`, and the complete ALCops suite `ensure-alcops` installs: `${analyzerFolder}ALCops.ApplicationCop.dll`, `${analyzerFolder}ALCops.DocumentationCop.dll`, `${analyzerFolder}ALCops.FormattingCop.dll`, `${analyzerFolder}ALCops.LinterCop.dll`, `${analyzerFolder}ALCops.PlatformCop.dll`, `${analyzerFolder}ALCops.Common.dll`.

- **Every single `al_compile`/`al_build` call this session, not "at least once."** Pass `enableCodeAnalysis=true` and this exact `codeAnalyzers` list explicitly, on every call, for the whole session — never omit the parameters and never trust the tool's "server startup configuration" fallback, even if `.vscode/settings.json` looks correctly configured. A workspace setting can be stale, missing, or not actually read by the al-mcp server process; the only way to *know* all analyzers ran is to name them yourself on the call that matters. Likewise, never let `onlyErrors=true` be your last word on a file — it's acceptable only for a throwaway fail-fast check mid-edit, never for the check that decides a file is done.
- **Check every file you create or edit, not just the build's pass/fail flag.** After compiling, pull **al-mcp** `al_getdiagnostics` scoped to each touched `filePath`/`folderPath` with no `severities` filter (or explicit `['error','warning']`) — a green build can still carry warnings on the exact lines you just wrote. Do this for every file, not a sample.
- **Zero new warnings is the bar — from any of these analyzers, not just the compiler core.** A pre-existing warning on a line you did not touch is not yours to fix (note it, don't block on it). A warning on a line you wrote or modified — including one introduced by refactoring, and including a LinterCop/FormattingCop/DocumentationCop/ApplicationCop/PlatformCop finding, not just an `AL####`/CodeCop one — must be resolved before the file is done, the same way an error would be. Don't rationalize a warning away as "just a style suggestion," "not blocking," or "that cop doesn't really matter here" — that framing is exactly rule 1 below, applied to a lower severity, and it is exactly the failure mode this section exists to close off.
- **Reviewers (al-review-subagent, dredd) verify this independently** rather than trusting the implementer's self-report — see the note at the bottom of this file.

1. **The compiler is ground truth for syntax validity.** A real `ALxxxx` diagnostic is evidence the code is wrong, not a claim to litigate. Never respond to a diagnostic by asserting the syntax is correct and the compiler is mistaken, outdated, or "doesn't support" something — that framing is backwards by default.

2. **Before rewriting the same construct a second time, verify it actually exists** — don't guess again from memory:
   - Confirm the real member/property/type/event signature with **al-mcp** `al_symbolsearch` / `al_symbolrelations` against the actual base object, or
   - Check the relevant `skill-*` reference for the documented pattern, or
   - Check `microsoft-docs` / `context7` for the current AL language/API surface.
   Ground the fix in something confirmed, not a second invented variant of the first guess.

3. **One invented-then-corrected attempt per diagnostic.** If the *same* error code recurs on the same construct after a grounded fix attempt, stop guessing — this is not a "try a third syntax variant" situation. Escalate as an open question (to the Conductor, or to the user if running standalone) with what was tried and what the symbol lookup actually showed.

4. **Never silently defer, stub, or comment out code because of a compiler error.** Dropping or deferring functionality to make a build pass is a scope change, not a coding decision — it requires explicit escalation (Unplanned Finding Triage / HITL), never a private workaround. Treat any `// TODO: re-enable/add at go-live`, `// not supported by compiler`, or similarly-motivated stub as something that must be flagged, not quietly shipped.

5. **"Compiler limitation" is only a valid conclusion when backed by a citation** — a Microsoft Learn page, a linked known-issue, or an al-mcp symbol lookup that confirms the construct genuinely isn't available in the referenced BC version/dependency. It is never the default explanation for an unresolved diagnostic, and it is never a reason to defer rather than find the correct working syntax.

**For reviewers (al-review-subagent, dredd):** treat rule 4's pattern as a MAJOR finding on sight — a defer/limitation-style comment next to disabled or stubbed code must be justified with the citation from rule 5, or reverted/fixed. Don't wave it through as a stylistic TODO. Also **re-run `al_getdiagnostics` yourself** (full severities, scoped to the files under review) rather than trusting the implementer's "0 errors" claim — the implementer's own report is exactly what rule 0 exists to keep honest. Any warning on a changed line that the implementer's summary doesn't account for is at minimum a MINOR finding; a pattern of unaddressed warnings across a phase is MAJOR (it means analyzers likely weren't actually enabled).
